# Research: MCP 状态与会话同步

## 面板状态刷新

- **Decision**: 面板挂载后立即读取快照，随后每 1 秒执行一次串行轮询。前一次请求结束后才安排下一次请求，卸载时清除计时器并使在途结果失效。
- **Rationale**: 现有状态路由已经返回完整快照。1 秒轮询满足 2 秒展示目标，串行调度避免慢请求堆积。
- **Alternatives considered**: 固定周期并行请求会堆积慢请求；新增状态推送接口会扩大宿主与路由契约；只刷新操作结果无法反映异步连接完成。

## 快照顺序

- **Decision**: 每次读取和直接写入快照都使用单调递增序号。只有最新序号可以更新快照或读取错误。
- **Rationale**: 自动刷新、手动刷新和表单操作可以并发，序号能阻止较早响应覆盖较新的操作结果。
- **Alternatives considered**: 只给轮询加序号不能覆盖手动操作；为所有操作增加全局串行队列会让表单保存等待状态请求。

## 会话目录注入

- **Decision**: 配置对账后向全部在线 Agent 注入目录，可见性变化后向调用方 Agent 注入目录。使用 `agent.inject()`，保留现有 `agent/pre-step` 兜底。
- **Rationale**: 当前宿主 `@deepseek-ai/dsh-agent@0.2.2-rc.3` 将注入消息持久化到下一步队列，不唤醒空闲 Agent。现有目录渲染、来源记录与投影可以直接复用。
- **Alternatives considered**: 只保留 `agent/pre-step` 会把通知延迟到下一步；唤醒 Agent 会产生用户未要求的模型活动；直接新增会话事件类型会破坏会话兼容性。

## 待处理目录去重

- **Decision**: 注入前比较当前待处理目录与待写入目录。下一步入口过滤本次消息批次里的全部旧目录，再补入至多一条最新目录。
- **Rationale**: 已注入消息在步骤准入前只存在于队列中，目录投影尚未折叠它。读取队列可以避免重复通知，入口合并可以保证连续变化只向模型呈现最新目录。
- **Alternatives considered**: 私有内存缓存会增加恢复与 fork 的一致性问题；允许所有待处理目录进入同一步会重复占用上下文。

## 测试与文档

- **Decision**: 用虚拟计时器验证轮询，用模拟 Agent 的持久队列验证注入、隔离、去重与连续变化。更新 README、工作机制与已知风险。
- **Rationale**: 这些测试覆盖实际状态变化与消息流。可见性行为和持久化时机的说明需要与实现保持一致。
- **Alternatives considered**: 静态渲染无法执行效果与计时器；仅做实机验证不能稳定覆盖慢请求和连续变化。
